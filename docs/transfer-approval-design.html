Transfer Approval System

Vision Bank corporate fund transfers pass a maker-checker control before release. Two independently deployable services split on a hard ownership line: Banking Service owns what a transfer means (submission, validation, release); Approval Engine owns how an approval progresses (workflow, policy, state, quorum, audit, expiry). Neither writes the other's database; they coordinate over the network. The approval mechanism is domain-independent — proven by a second workflow (privileged-access) running on the same engine with zero code change.

Each hop uses the pattern its failure mode demands, not one style uniformly. Neither service's uptime gates the other's. At-least-once is safe because every consumer was already idempotent (§4).

§4Non-Functional

Idempotency

POST /transfers and POST /approvals take an Idempotency-Key; same key + same body replays the result, same key + different body → 409 IDEMPOTENCY_CONFLICT. Decisions (approve/reject/cancel) are idempotent per (request_id, actor_id, state) — a checker's intent is the natural key. Release is idempotent on transferId. This is what makes at-least-once redelivery safe with no second correctness mechanism.

Consistency

Strong/transactional within each service (one local ACID transaction per state change: state + audit + outbox commit atomically); eventually consistent across the boundary — no distributed transaction. Resilience is symmetric: Engine down doesn't break submit(); Banking down doesn't break approve/reject/cancel — only event delivery waits.

Partial failure

A crash between "decision recorded" and "event delivered" never loses the decision — it only delays the counterparty finding out; the reconciler on each side closes the gap.

Part II — Low-Level Design

§7Approval State Machine (Engine)

APPROVED means the approval requirement is satisfied — not that money has moved. Below is the common shape; transfer-auto-release has only the top edge, single/high-value only the bottom five.

privileged-access:2 (≥ AED 100,000, the live top tier) replaces the single PENDING_APPROVAL with a three-stage chain — same engine, no special-casing: reject and expire [sla_expired] are each legal from all three review stages, converging on shared REJECTED/EXPIRED terminals below. It has no cancel edge at all, unlike the transfer workflows: a privileged-access request has no maker in the transfer sense to withdraw it.

Each stage is its own PENDING_APPROVAL-equivalent, but Transfer's own lifecycle (§8) still only ever sees the generic PENDING_APPROVAL — it has no visibility into which of the three review stages the engine is currently on, only whether the request is still pending or has reached a terminal state.

§8Transfer Lifecycle (Banking)

CREATED is the brief async gap between POST /transfers returning and its creation command being consumed off stream:transfer-approval-create (approvalRequestId is null throughout; GET reports it honestly) — normally sub-second, longer only if the Engine is down, in which case the command simply waits in the stream rather than the request failing. FAILED is not necessarily terminal: resuming with the same Idempotency-Key (TransferSubmissionService.resumeIfNeeded) republishes the creation command, and ApprovalEventListener links the resulting workflow exactly as it would from CREATED. FAILED is deliberately generic for its one current cause (SubmissionCommandReconciler giving up after its delivery-attempt ceiling); a second failure mode should split by cause (e.g. add RELEASE_FAILED) rather than overload this one with a reason code. No RELEASE_FAILED today — a transient core-banking failure retries in place.

§9Approval ↔ Transfer Correspondence

These are two independent state machines, not one shared one: the Engine never queries Transfer's state, and Transfer never queries the Engine's beyond consuming its events.

Notably, ApprovalCommandService.create() writes ApprovalSubmitted unconditionally on every creation — even transfer-auto-release, whose YAML only declares an APPROVED event — which is why Transfer always sees CREATED → PENDING_APPROVAL before RELEASE_PENDING; there is no code path straight from CREATED to RELEASE_PENDING. Every reaction above is also conditional on Transfer still being in the expected state, so at-least-once redelivery is always a no-op, never a duplicate state change or notification.

§10Workflow Definitions & Policy Contract

Every workflow YAML under approval-engine/.../workflow/definitions/ declares its own states, transitions, and per-transition allowedRoles/requiredApprovals — routing between tiers happens before the engine, by picking which workflow to instantiate, not by a guard branching inside one shared workflow. Five concepts nest strictly, top to bottom:

A Policy row only ever picks a (workflowId, workflowVersion) pair — it has no opinion on stages, transitions, guards, or quorum. Everything below Workflow is that workflow's own business, declared once in its YAML and looked up by name at runtime, never computed from the policy that routed to it. requiredApprovals is a field on Transition itself — not a workflow-level or policy-level setting. Absent/null means the transition is unconditional (transfer-auto-release's only transition has none); any positive integer N means the approvals_satisfied guard blocks the transition until N decisions matching allowedRoles are recorded for the current stage. Because it's per-transition, not per-workflow, a single workflow can demand a different N at each stage — privileged-access requires 2 at SECURITY_REVIEW but only 1 at each of MANAGER_APPROVAL and COMPLIANCE_REVIEW — with no special-casing anywhere in the engine.

policy_rule(id PK, min_amount_minor_units, max_amount_minor_units nullable, workflow_id, workflow_version) is an editable table in Approval Engine, not a formula in Banking. GET /policy-rules/resolve?amountMinorUnits=N returns the first row covering N (404 POLICY_RULE_NOT_FOUND if none does). Resolution now happens in-process inside the Engine's SubmissionCommandConsumer (via PolicyRuleResolutionService) when it consumes the creation command off stream:transfer-approval-create — not a synchronous call out of Banking. The resolved workflow is frozen into policy_snapshot at creation and never re-resolved, so an in-flight request keeps its version even if the rule changes.

As-built caveat: Banking's PolicyResolver/ApprovalEngineClient.resolvePolicy() classes still exist in source but have zero callers — dead code, left in place since policy resolution moved into the Engine.

§13Sequence Diagrams

(a) Auto-release (0 approvals required)

  1. 1Banking: persistCreated() → CREATED, returns immediately
  2. 2Banking → stream:transfer-approval-create: XADD (transferId, makerId, amount, expiresAt)
  3. 3Engine SubmissionCommandConsumer: XREADGROUP, resolves transfer-auto-release:1 in-process (PolicyRuleResolutionService)
  4. 4Engine commits: state + audit + outbox(ApprovalSubmitted, ApprovalApproved); XACK
  5. 5Outbox relay claims (FOR UPDATE SKIP LOCKED), XADDs both events to stream:approval-lifecycle-events
  6. 6Banking LifecycleEventConsumer: dedupes by event_id, links CREATED→PENDING_APPROVAL, then releases → RELEASE_PENDING → RELEASED

(b) Multi-approver — quorum accumulation, required=2, no race

  1. 1Checker A → Engine: POST /approve
  2. 2SELECT … FOR UPDATE; count=0 < required=2 → guard fails, no state UPDATE
  3. 3Records decision (A, APPROVE); commits; count is now 1
  4. 4Engine → A: 200 PENDING_APPROVAL, v1 — quorum not yet met
  5. 5Checker B → Engine: POST /approve; SELECT … FOR UPDATE, count=1 still < 2 at read time
  6. 6Records decision (B, APPROVE); count is now 2 → guard now passes
  7. 7Guarded UPDATE WHERE state=PENDING_APPROVAL AND version=1 → rows=1 → APPROVED, v2; Engine → B: 200

Ground truth: ApprovalCommandServiceApproveTest.

(b′) Concurrent-approve race (required=1, same slot, exactly one wins)

  1. 1Checker A and Checker B both POST /approve
  2. 2A: SELECT … FOR UPDATE (lock acquired); B: SELECT … FOR UPDATE (blocks on A)
  3. 3A: guard passes, UPDATE WHERE state=PENDING_APPROVAL AND version=1 → rows=1, commits (APPROVED, v2), lock released
  4. 4Engine → A: 200 APPROVED, v2
  5. 5B: lock granted, reads state=APPROVED (not PENDING_APPROVAL)
  6. 6Engine → B: 409 CONCURRENT_STATE_CHANGE (currentState APPROVED)

Ground truth: ApprovalConcurrencyTest.twoCheckersApprovingSimultaneously_exactlyOneWins.

(c) Expiry vs. approve (optimistic race, no row lock on the sweeper's path)

  1. 1Sweeper: expireOne(id, expectedVersion=1)
  2. 2Checker (concurrently): POST /approve
  3. 3Both race: UPDATE WHERE state=PENDING_APPROVAL AND version=1 → EXPIRED vs. → APPROVED
  4. 4Exactly one UPDATE affects rows=1; the other rows=0 → no-op / 409

Ground truth: ExpiryVersusApproveConcurrencyTest.approveVersusExpire_exactlyOneWins.

§14Concurrency / Race Handling

Every competing transition resolves through one guarded conditional UPDATE:

UPDATE approval_request SET state = :new_state, version = version + 1
 WHERE request_id = :id AND state = :expected_state AND version = :expected_version;
-- rows=1 -> won ; rows=0 -> lost race or illegal transition (whole txn rolls back)

On rows=0 the whole transaction rolls back (decision insert, audit, outbox — all of it); re-reading current state then classifies the failure: 409 CONCURRENT_STATE_CHANGE if it was a legal predecessor, 409 INVALID_STATE_TRANSITION if it could never have led here.

Quorum counting additionally takes a SELECT … FOR UPDATE row lock (ApprovalCommandService.loadOrThrow) — a deliberate exception to "no explicit locks," since counting committed decisions is an aggregate read the guarded UPDATE alone can't protect: without it, two checkers can each count only their own still-uncommitted vote, both see quorum unmet, and a request that actually has enough approvals is stranded in PENDING_APPROVAL forever.

Why a lock, not a lock-free alternative: considered and rejected for this contention shape (at most requiredApprovals actors, one row, a millisecond-scale critical section) — an atomic counter column drops the explicit lock but denormalizes the count against approval_decision as a second source of truth that can drift; SERIALIZABLE isolation + retry trades a short wait for a full abort-and-redo, for contention this shallow; splitting "record vote" from "evaluate quorum" into two transactions closes the race without a lock but turns a synchronous decision eventually-consistent for no real gain at this scale. A PESSIMISTIC_WRITE held for one short cycle, on one row, contended by a handful of actors, is the simplest option that's actually correct.

The same guarded UPDATE covers every other competing pair for free, with no special-casing per transition — including the maker-cancel-vs-checker-approve race: cancel and approve are both guarded transitions out of PENDING_APPROVAL, so whichever UPDATE … WHERE state='PENDING_APPROVAL' AND version=? commits first wins; the other affects 0 rows and is classified the same way as any other lost race. The console additionally hides an actor's own approve/reject buttons once they've already decided the active stage — a UX nicety, not a control: the server-side UNIQUE(request_id, actor_id, state) constraint is what actually blocks a double decision (a contradictory second decision gets 409 IDEMPOTENCY_CONFLICT); the client guard just avoids surfacing that as an error to someone who already knows they voted.

Evidence: ApprovalConcurrencyTest (two-checkers, cancelVersusApprove_exactlyOneWins), ExpiryVersusApproveConcurrencyTest.

§15Redis Stream Delivery

Two streams, one consumer group each: stream:transfer-approval-create (approval-engine-workers) and stream:approval-lifecycle-events (banking-service-workers). Both are at-least-once — a message stays in the group's pending-entries list until XACK'd; SubmissionCommandReconciler / LifecycleEventReconciler reclaim anything idle past 30s via XPENDING + XCLAIM (the Redis-native equivalent of OutboxClaimService's claimed_at staleness window) and retry it.

The submission side additionally gives up after 3 delivery attempts, publishing ApprovalCreationFailed onto the lifecycle stream so Banking can move the transfer to FAILED and notify the maker — the lifecycle side has no equivalent failure state to move to, so it logs loudly past 5 attempts rather than silently dropping the message (a full dead-letter mechanism is out of scope).

Redelivery is safe everywhere it can happen because every consumer here was already idempotent before Redis existed: ApprovalCommandService.create() by (Idempotency-Key, body hash), ApprovalEventListener.handle() by processed_event.event_id.

What I'd do with more time

  • Funds hold/reservation between validate and release — the one named gap; a hold()/free() contract with Core Banking closes the concurrent-overspend window.
  • Real authentication — replace the trusted X-Actor-Id/X-Actor-Role headers with proper token-based authN/Z (OIDC/JWT at the gateway, role claims verified server-side), so maker/checker identity and eligibility aren't caller-asserted.
  • Reporting UI — a console view over the audit trail: transfers by state/tier/maker, SLA breaches, per-checker decision history — turning audit_log into an operational and compliance surface.
  • Workflow create/edit UI — a screen to author and version workflow definitions (stages, transitions, allowedRoles, requiredApprovals) and edit policy_rule ranges, so tiers change without hand-editing YAML — the engine already treats these as data.
  • Better concurrency than PESSIMISTIC_WRITE — the row lock is correct but coarse; under real load, evaluate a monotonic per-stage approval counter with a conditional guarded write, or advisory locks scoped to request_id, to shrink the held critical section.
  • Rate limiting — per-maker and per-actor limits at the gateway (token-bucket) to protect against runaway retries and abuse, distinct from idempotency (which handles correctness, not volume).
  • Priority queue for high-value transfers — a separate high-priority consumer group / stream so high-value and privileged-access approvals aren't stuck behind a backlog of low-tier auto-releases; time-sensitive money moves first.
  • Dead-letter queue for messages past max delivery attempts, instead of logging loudly.
  • Physically separate the two Postgres DBs so "neither service writes the other's DB" is enforced by infra, not convention.
